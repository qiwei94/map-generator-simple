## 三个必须收尾的问题

### 1. 最新整城桥梁仍阻塞

`output/paris_25km_C_formal_20260908_v4/` 中没有 3MF。原始
`pipeline_measurement_report_s7.json` 的 `generation_outcomes.building_mass.final_surface_plan.grounding.roads`
记录 150 个桥面片，11 个 ready，139 个 blocked（面片数不是桥梁座数）：

- 93：单一桥梁源线无法覆盖合并面，需要多线/多桥衔接。
- 24：裁切丢失水外两岸支撑。
- 19：弯桥沿线高程策略未实现。
- 3：岸部横断面仍部分处于水中。

代码 `aesthetic/road_grounding.py::_bridge_patch` 仍明确拒绝这些情况。
这是表达能力与接驳算法缺口，增加等待时间不会使同一任务成功。
应先对每类固定真实样本完成局部回归，再运行整城；不删除失败桥片，不放宽门禁。
如选择“贴水浮雕连接”，必须先明确这是新的产品表达，再实现显式模式，不能自动回退。

### 2. B＋C 没有成为网页固定方案

`generate_city_legacy.py` 默认 `urban_organization=default`、`surface_road_style=printer-default`。
S5 只在 active 且 C/block-first 时加入 z_texture；`webapp/server.py` 的普通生成命令
没有传这两个选定参数。因此“已经接入代码”不等于“网页普通任务已使用选定方案”。
首件入口应固定选定配置并在报告中记录；通过完整验证后再推广网页。

### 3. 最新实现尚未形成版本检查点

本次核查基线：分支 `agent/final-block-base-clearance-v17`，HEAD `3915c54`
（2026-09-05）。核查时有 34 个已跟踪文件修改，以及多项未跟踪实现、测试和文档。
`git diff --stat` 不包含未跟踪代码，不能仅凭该统计描述全部改动。
演示包记录源码文件哈希；它不代替 Git 提交或包含数据缓存的可复现环境。

## 建议固定的首件交付合同

第一版只收尾巴黎一个 25 km 框：48.74355353,2.18153414,48.96964647,2.52286586。
沿用已有 PBF/DEM、block-first 完整街道、negative-space-fine-v1 与已选 B＋C。
0.14/0.21 mm 街缝和 0.07 mm 起伏保留为视觉选择；实际可打印程度由切片确认。

按以下顺序执行，全部完成才称“首件打印候选完成”：

1. 将当前代码形成可恢复检查点，保存实际配置、数据身份和运行环境。
2. 用上述四类桥梁真实样本补齐连续源线、岸部支撑和沿线高程；通过后再整城。
3. 一次完整主入口生成，测量纹理面数预算、内存与耗时，取得 PNG、GLB、3MF 和同次 DesignSpec。
4. 对实际 3MF 执行项目严格验证，要求 0 errors / 0 warnings；核对桥梁、水体和街块无遗漏。
5. 对同一文件完成目标打印机切片，检查桥岸支撑、街缝封闭及微纹理保留；归档文件哈希和证据。

多城市泛化、新数据融合、参考图像素追赶、额外边缘/地标美化及架构重写不进入首件关键路径。
只有直接阻塞以上验收的缺陷进入本阶段修复。
如果整城纹理超预算，应显式提出精度调整并验证效果，不能静默舍弃已选纹理。
当前没有实测完整 B＋C 25 km 成功耗时，旧会话的 20–40 分钟只可视作估算。
